# Seed a demo user in the current application

> Historical implementation stages: the initial synthetic seed was replaced by
> validated provider history, then extended to five years with action accounting.
> See `2026-11-04-five-year-demo.md` and the current README for final behavior.

User requested a demo user in the existing environment instead of a separate stack.

Design: an explicit `seed:demo` command adds username `demo` with synthetic historical activity under one reserved user ID. It uses the normal runtime database role and normal password hashing/login. There is no auto-seeding at startup, authentication shortcut, provider switch, schema change or resetting of existing users. A first run generates a password (or accepts `DEMO_PASSWORD`); a rerun does not alter credentials or subsequent activity. An existing unrelated `demo` username/email causes a conflict. Production invocation is refused.

Seed all rows in one transaction under a seed advisory lock. Include three holdings, five filled trades with exact ledger/cost records, pending/cancelled/expired/rejected order examples, folders/watchlist, notes, active/triggered alerts, a notification and historical portfolio snapshots. Historical demo prices are synthetic and scoped to demo executions/snapshots; never write shared quote, FX or statistics observations or overwrite existing instrument metadata. Missing catalogue metadata may be inserted for the configured provider. Current valuations continue using normal market data and may initially be unavailable until the worker refreshes it.
